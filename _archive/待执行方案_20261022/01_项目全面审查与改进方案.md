## 二、代码质量改进层（优先级 P1 — 一周内）

### 2.1 mainwindow.cpp 职责拆分

**现状**：1265 行，承载 PTZ 方向盘绑定、镜头控制、跟踪 UI、鼠标框选、图像显示、录像控制、数据记录转发等 7+ 类职责。

**方案**：按 MVC 分离出以下独立模块：

| 新模块 | 从 mainwindow.cpp 拆出的职责 | 预估行数 |
|--------|------------------------------|----------|
| `PtzPadWidget` | 方向盘 8 键 + stop 信号绑定（L83~L133） | ~80 |
| `LensControlWidget` | 变焦/聚焦/光圈按钮绑定（L136~L211） | ~100 |
| `TrackingPanel` | 框选模式 + 参数读取 + 状态显示 + 鼠标事件（L1016~L1265） | ~250 |
| `VideoDisplay` | displayImage + drawTrackBoxOnPixmap + m_scaledPixmap 缓存 | ~100 |

**约束**：拆分后各 Widget 仍在主线程，仅改善代码组织，不改变线程模型。

### 2.2 ConfigManager 默认值与 TrackingController 默认值不一致

**问题发现**：

| 参数 | TrackingController 默认值 | ConfigManager 默认值 | 说明 |
|------|--------------------------|---------------------|------|
| Kp | 0.5 | 0.15 | **不一致** |
| Ki | 0.02 | 0.005 | **不一致** |
| Kd | 0.3 | 0.03 | **不一致** |
| Kff | 0.15 | 0.5 | **不一致** |
| T_predict | 2 | 5 | **不一致** |
| DeadZone | 20 | 15 | **不一致** |

**分析**：TrackingController 构造函数中的默认值（README 第五节描述的设计值）与 ConfigManager 持久化的默认值完全割裂。实际运行时，`on_btnTrackStart_clicked` 从 UI 控件读值，而 UI 控件初始值取决于 ConfigManager 的 loadConfig()。因此**用户实际使用的参数是 ConfigManager 的默认值**，TrackingController 构造函数的默认值仅在首帧（setTarget 之前）短暂存在。

**修复方案**：
1. 以 TrackingController 的设计值为权威源，ConfigManager 默认值对齐。
2. 或者反过来——以 ConfigManager 为权威源（更合理，因为支持运行时调参和持久化）。
3. **推荐方案 B**：删除 TrackingController 构造函数中的硬编码默认值，改为 `initTrackingModule()` 阶段从 ConfigManager 同步。同步更新 README 第五节。

### 2.3 PTZ 方向速度 Pelco-D 安全限幅遗漏

**问题**：`onPtzControlDelta()` 中将 `speedX/speedY`（int，可能为负数）直接 `static_cast<uint8_t>`，负数会溢出为大值。虽然 `moveDirection()` 内部有 `> 0x3F` 的 clamp，但在 cast 阶段已经丢失了语义。

**修复**：在 cast 之前加 `qBound(0, abs(speed), 63)`，或者直接在 `computePTZControl` 输出阶段保证 abs(speed) ≤ 63。

### 2.4 KF 状态矩阵手写展开的维护风险

**现状**：`kfPredict()` 和 `kfUpdate()` 中 4×4 矩阵运算全部手写展开（约 120 行），虽然避免了动态分配，但：
- 矩阵公式如果有变（如增加加速度状态到 6 维），手工展开完全无法维护
- 当前 `A*P*A' + Q` 的展开是否正确难以人工审查

**建议**：引入一个 4×4 小矩阵的 inline 工具类（或直接用 `cv::Matx44f`），把 predict/update 改写为标准 KF 公式的矩阵调用。OpenCV 的 `Matx` 是栈分配的，零堆开销。

### 2.5 DataRecorder 增量写 CSV 的异常安全

**R-05 问题**：`startRecording()` 中 `new QFile / new QTextStream` 在 `stopRecording()` 中 `delete`，如果程序异常退出（崩溃/断电），文件句柄不会释放。

**修复**：改为 `std::unique_ptr<QFile>` + `std::unique_ptr<QTextStream>`，或者用 Qt 父子树托管。同时在 `aboutToQuit` 中显式调用 `stopRecording()`。

### 2.6 DsstCore 极小目标的 `numScales` 下溢

**R-10 修复了 `minScale > maxScale`**，但根因是当目标极小（如 8×8）时 `numScales=9` 可能导致部分尺度因子使采样区域超出图像边界。建议在 `init()` 中增加 `m_numScales = std::min(m_numScales, 合理上限)` 的运行时校正。

## 三、架构优化层（优先级 P2 — Step 7 联调前后）

### 3.1 跨平台构建支持

**现状**：`.pro` 中 OpenCV 路径仅有 `win32:` 分支，Linux 和 macOS 未覆盖。`sdk/` 下 `.lib/.dll` 是 Windows 特有格式。

**方案**：
```qmake
win32: LIBS += -L$$OPENCV_DIR/x64/mingw/lib -lopencv_core4100 -lopencv_imgproc4100
unix:  LIBS += -L$$OPENCV_DIR/lib -lopencv_core -lopencv_imgproc
```
同时为 `sdk/` 增加 `unix:` 分支（指向 `sdk/univisionsdk-0.3.2/` 中的 `.so`）。

### 3.2 引入 QTest 单元测试框架

**目标**：为 DsstCore、KF、PID 控制逻辑建立自动化回归测试。

**方案**：
1. 新建 `tests/` 目录 + `tests.pro` 子工程
2. 重点覆盖：
   - `DsstCore::init + update` 的边界条件（空图/极小框/极大框）
   - `computePTZControl` 的死区/限幅/积分饱和行为
   - `ThreadSafeQueue` 的并发 push/pop/stop/reset
   - `buildPelcoDPacket + calculateChecksum` 的协议正确性
3. CI 集成：`qmake && make && ./tests`

### 3.3 性能监控仪表盘

**联调需求**：Step 7 的 7.5（CPU 占用评估）和 7.6（24h 内存泄漏检查）需要运行时指标。

**方案**：在 MainWindow 状态栏或独立面板实时显示：
- 跟踪器 FPS（已有 `result.fps`）
- 解码队列深度（`m_dataQueue.size()`）
- 丢帧计数（`m_dataQueue.droppedCount()`）
- KF 状态向量（kfX/kfY/kfVx/kfVy）
- PID 输出（speedX/speedY/integralX/integralY）
- PTZ 实际角度（来自 `angleReceived` 信号）

### 3.4 录像与预览共享解码优化（V4 架构项）

**现状**：录像线程和预览线程各自独立解码同一路 H.264/H.265 码流，CPU 开销翻倍。

**方案**（优先级较低，待 Step 7 验证 CPU 确实是瓶颈后再做）：
- SDK 回调将原始码流分发给一个共享 `VideoDecoder`
- 解码后的帧通过 fan-out 同时送入预览队列和录像队列
- 录像队列接收 `AVFrame` 而非 `QByteArray`，避免二次解码

### 3.5 DeviceManager 单例模式改进

**现状**：`DeviceManager::instance` 是裸静态指针 + `QMutex` 保护，在析构顺序不确定时有风险。`CaptureManager` 也是同样模式。

**建议**：改为 Qt 标准的父子树 + 依赖注入（当前 MainWindow 已经通过构造函数管理生命周期），取消全局 `instance` 指针。SDK 回调中改为捕获 `QPointer<DeviceManager>` 或通过信号中转。
