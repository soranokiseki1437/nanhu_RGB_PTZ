## 二、 核心开发守则：GPU 高效验证与 RK3588 边缘落地的“零冲突铁律”

当前开发机配备了顶级的 **NVIDIA RTX 5070 GPU**，为避免在 PC 高算力环境下过度设计导致后续边缘端（RK3588 6 TOPS NPU）移植失败，全体方案执行必须严格遵守以下 **三大零冲突铁律**：

```
                    【开发验证阶段：Windows (RTX 5070 GPU)】
                 [ 标准静态模型: yolo11s.onnx / yolo11n.onnx ]
                                     │
                     ┌───────────────┴───────────────┐
                     ▼                               ▼
       [ 推理后端 OnnxDetector ]           [ 纯 C++ 业务层 ]
       (DirectML 显卡硬件极速加速)        • YoloPostProcessor (纯 C++ NMS)
                     │                  • ByteTrack (纯数学矩阵关联)
                     │                  • TargetSelector (主目标锁定)
                     │                  • TrackingController (前馈+PID)
                     │                               ▲
    ═════════════════╪═══════════════════════════════╪═════════════════ (跨平台分界线)
                     ▼                               │
                    【未来落地阶段：RK3588 (ARM64 + NPU)】
                 [ 转换后的量化模型: yolo11s.rknn (INT8) ]
                                     │
                     ┌───────────────┴───────────────┐
                     ▼                               │
       [ 推理后端 RknnDetector ]                     │
       (调用 librknnrt.so 驱动 NPU) ──────────────────┘ (业务代码 100% 原封不动复用！)
```

1. **模型尺寸克制律（禁止贪大）**：
   - 虽然 RTX 5070 跑 `YOLO11m/11l` 依然很快，但为了 RK3588 算力对齐，**严格限制候选模型尺寸为 `nano (n)` 与 `small (s)`**。
   - `YOLO11s` 在 RTX 5070 上约为 3~5ms，在 RK3588 NPU (INT8) 上约为 20~25ms，均能稳稳满足 $\ge 30\text{ fps}$ 云台伺服实时性。
2. **算子中立导出律（禁止 GPU 绑定算子）**：
   - 导出 ONNX 时必须为标准静态尺寸（$1 \times 3 \times 640 \times 640$），采用通用 OPSET 12/17；
   - 严禁将 TensorRT 专属插件、CUDA 私有算子或 NMS 打包进模型，保证 `rknn-toolkit2` 能够 100% 自动量化转换。
3. **前/后处理代码纯净律（纯标准 C++ 编写）**：
   - `YoloPostProcessor`、`ByteTrack` 等数据解析与跟踪层严禁手写任何 `.cu` 或平台私有指令，保持纯标准 C++ 与 OpenCV core，确保直接在 Linux aarch64 上原生编译。

## 三、 方案生命周期流转机制

每一个新建或修改的方案均遵循以下五阶段生命周期：

```
 [ 草拟 (Draft) ] ──▶ [ 评审就绪 (Ready) ] ──▶ [ 执行中 (In Progress) ]
                                                        │
                      [ 历史归档 (Archived) ] ◀── [ 已闭环 (Completed) ]
```

1. **草拟阶段 (Draft)**：
   - 命名必须严格遵守：`0X_方案核心简述.md`（0X 为两位递增数字编号）。
   - 必须包含：**目标背景、架构设计、落地步骤（Checklist）、成果验收基准**四要素。
2. **评审就绪 (Ready)**：
   - 确认与现有工程代码（多线程模型、云台串口、现有 DSST）无架构冲突。
   - 确认符合第二节的“跨平台零冲突铁律”。
3. **执行中 (In Progress)**：
   - 同步更新本文件状态为 `🟡 进行中`。
   - 严格按方案内部的阶段 Checklist 逐步推进代码落地与编译调试。
4. **已闭环 (Completed)**：
   - 所有 Checklist 勾选完毕，且通过方案所列的成果验收指标。
   - 在 [checkpoint.md](file:///d:/PyProjects/RGB_PTZ_Integrated/checkpoint.md) 中记录里程碑与 Git Commit ID。
5. **历史归档 (Archived)**：
   - 废弃或已被替代的历史方案转移至 `_archive/待执行方案_YYYYMMDD/` 备份，避免工作区混乱。

## 四、 与 `checkpoint.md` 事实源的强联动规则

为杜绝“方案脱节”、“代码跑偏”和“跨会话遗忘”，执行方案时必须遵守以下铁律：

1. **进场必读**：开始执行任何方案前，先检视 [checkpoint.md](file:///d:/PyProjects/RGB_PTZ_Integrated/checkpoint.md) 当前工程编译状态、未决问题与未提交改动。
2. **里程碑必记**：当方案完成一个核心阶段（例如：方案 01 阶段一完成 ONNX 单图推理测试）：
   - 执行 `git status` 确认工作区清洁；
   - 编译 Release 并确保 **0 Error / 0 Warning**；
   - 在 `checkpoint.md` 历史记录中追加阶段条目。
3. **零破坏铁律**：
   - 任何深度学习改动不得破坏现有系统已有功能（视频流 30fps 解码、传统 DSST 框选跟踪、Pelco-D 云台串口收发与限位保护）。
