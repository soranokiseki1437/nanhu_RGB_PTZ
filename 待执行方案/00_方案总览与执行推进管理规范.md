## 二、 系统架构：业务双轨协同与硬件分工基准

### 2.1 业务双轨协同拓扑：索敌感知 (MOT) 与 视轴死锁 (SOT)

光电云台在物理上为单一视轴转动设备，系统算法层明确解耦为前后级接力架构：

```
                    【阶段一：目标检测阶段 (Target Detection Phase)】
                     (方案 01 / 方案 03: YOLO11 + VaL_CNN 二级校验 + ByteTrack 广域感知)
                     • 职责：全图视野搜索、多目标候选识别、操作员“点击锁定 (Click-to-Lock)”前置输入、
                            以及跟踪阶段失锁时的“单次按需重捕获 (Re-detection On-Demand)”
                     • 频度：常态处于 0 FPS 休眠 (零算力占用)；索敌/失锁时单次唤醒运行 1 帧
                     • 数据集规范：使用【目标检测数据集 (Object Detection Dataset)】，避免使用单目标连续跟踪切片混淆检测训练。
                                         │
                                         ▼ (交接主锁定目标 TrackResult: 中心坐标与尺度)
                    【阶段二：目标跟踪阶段 (Target Tracking Phase)】
                     (方案 02: DSST / 方案 04: LightTrack 深度单目标跟踪)
                     • 职责：独占 30~60 FPS 高频运行，单帧延迟 < 4ms
                     • 实时计算单一脱靶量 (dx, dy)，直接闭环驱动 PID 与云台电机
                     • 数据集范围：单目标跟踪基准 (SOT Video Sequences)
                                         │
                                         ▼ (当 SOT 可靠度突降 / 发生遮挡)
                    【顶层调度大脑：方案 02 AMFT 状态机】
                     • 多特征动态评估，当综合得分低于阈值时，单次异步唤醒检测阶段做 1 帧全局检索；
                     • 重新捕获目标后，下一帧切回跟踪阶段并重置跟踪模板。
```

### 2.2 开发调试与边缘落地的分工基准

系统研发严格遵循**“Windows 平台高效验证，底层规范对齐边缘，最终集中量化移植”**的工程原则：

```
                    【开发与验证主阵地：Windows (RTX 5070 GPU)】
                 [ 标准静态 ONNX: yolo11s.onnx / sot_lighttrack.onnx ]
                                         │
                         ┌───────────────┴───────────────┐
                         ▼                               ▼
           [ 推理后端 OnnxDetector / OnnxSot ]     [ 纯 C++ 业务层 ]
           (DirectML 硬件极速推理，3~5ms)         • YoloPostProcessor (纯 C++ NMS)
                         │                       • AMFTEvaluator 协同状态机
                         │                       • TrackingController (前馈 + PID)
                         │                       • PTZController 串口驱动
                         │                               ▲
    ═════════════════════╪═══════════════════════════════╪═════════════════════ (阶段分界线)
                         ▼ (方案 05 边缘落地)            │
                    【最终落地目标：RK3588 (ARM64 + NPU)】
                 [ 转换后的量化模型: *.rknn (INT8) ]       │
                         │                               │
           [ 推理后端 RknnDetector / RknnSot ]           │
           (librknnrt 驱动 6 TOPS 三核 NPU) ──────────────┘ (业务与伺服代码 100% 复用)
```

1. **模型规格克制设计**：
   - 模型选型限制为 `nano (n)` 与 `small (s)` 级别，确保算力需求与嵌入式 NPU 承载上限保持一致；
2. **算子中立导出设计**：
   - 导出 ONNX 时固定静态输入尺寸（如 $1\times 3\times 640\times 640$ 或 $1\times 3\times 255\times 255$），采用通用 OPSET 12/17，避免引入平台专属私有算子；
3. **算法逻辑纯净设计**：
   - 前后处理、坐标变换与跟踪逻辑均采用纯标准 C++17 与 OpenCV core 编写，保障代码跨平台可移植性。

## 三、 方案生命周期流转机制

每一个新建或修改的方案均遵循以下生命周期：

```
 [ 草拟 (Draft) ] ──► [ 评审就绪 (Ready) ] ──► [ 执行中 (In Progress) ]
                                                        │
                      [ 历史归档 (Archived) ] ◄─── [ 已闭环 (Completed) ]
```

1. **草拟 (Draft)**：
   - 命名规范：`0X_方案核心简述.md`（0X 为两位递增编号）。
   - 必备要素：**系统定位、数学模型与架构、落地推进路线图（Checklist）、成果验收判定基准**。
2. **评审就绪 (Ready)**：
   - 确认与现有工程代码（多线程模型、云台串口、现有跟踪器接口）接口自洽。
   - 确认符合第二节的模型设计约束。
3. **执行中 (In Progress)**：
   - 同步更新本总览状态为 `🟡 进行中`。
   - 严格按方案内部的阶段 Checklist 逐步落地代码、编写测试工具并调试。
4. **已闭环 (Completed)**：
   - 所有 Checklist 勾选完毕，且通过方案所列的成果验收指标。
   - 在 [checkpoint.md](file:///d:/PyProjects/RGB_PTZ_Integrated/checkpoint.md) 中记录里程碑与阶段结论。
5. **历史归档 (Archived)**：
   - 已被完全替代或完成使命的独立草案转移至 `_archive/` 备份。
