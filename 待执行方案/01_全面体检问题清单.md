## 一、跟踪模块（与移植直接相关）

### T1【P1】FFT 非二次幂长度时频域截断，破坏数学一致性
- 位置：fftutils.cpp:47-73（fft1d 补零分支）、fftutils.cpp:78-99（fft2d 调 fft1d）
- 证据：
  ```cpp
  int n2 = 1;
  while (n2 < origN) n2 <<= 1;      // 160 → 256
  std::vector<std::complex<float>> padded(n2, ...);
  fft1dCore(padded, inverse);
  for (int i = 0; i < origN; ++i) data[i] = padded[i];  // 频域截断回160
  ```
- 问题：160 点信号补零到 256 做 FFT 后截取前 160 个频点，既不是 160 点 DFT 也不是 256 点 DFT。正/逆变换都截断后，等效于对响应图做了一次无物理依据的低通滤波，峰值变钝、定位精度下降。
- 修复方向：模型尺寸统一取 2 的幂（配合 T2）；或整个链路统一使用补零后长度 N2；移植 OpenCV dft 后（见移植方案）此问题自然消除。

### T2【P1】跟踪模型尺寸不取 2 的幂，所有 FFT 都走错误分支
- 位置：objecttracker.cpp:199-202
- 证据：
  ```cpp
  // 直接使用原始尺寸，不强制 2 的幂次（与参考实现一致）
  m_modelW = rawModelW;   // 例：64目标×(1+1.5padding)=160，非2的幂
  ```
- 问题：与 T1 叠加，跟踪器全流程 FFT 均触发补零+截断分支。
- 修复方向：不单独修——`nextPow2` 会过度撑大模型、稀释响应峰值，与 objecttracker.cpp:199-200 已有的取舍注释一致；T1/T2 统一由 DSST 移植（OpenCV dft）解决。仅当最终放弃移植时，才考虑整条链路统一使用补零后的长度 N2。

### T3【P1】跟踪器性能不满足实时要求
- 位置：objecttracker.cpp:623-648（updateFilter）、objecttracker.cpp:87-119（imageToGray）、fftutils.cpp 全部
- 证据：数据结构为 `std::vector<std::vector<std::complex<float>>>`，160×160 模型每帧需多次整体深拷贝（每层 25600 次独立堆分配）；FFT 为手写 O(N²logN) 迭代版且逐行逐列调用；reDetect 时计算量再 ×9。
- 问题：25fps 下单帧预算 40ms，当前实现（灰度转换+采样+2次FFT2D+滤波器更新）单帧可达 40~100ms，实时性不足。
- 修复方向：正是移植 reference（OpenCV Mat + cv::dft + GST/HOG 特征）的动机所在，见《03_DSST移植详细方案》。

### T4【P2】跟踪每帧输出大量 qDebug，与日志锁叠加成性能瓶颈
- 位置：objecttracker.cpp:769-811（update() 内 8+ 条 qDebug）
- 问题：LogManager 每条日志全局 mutex + 同步 flush（见 L1），Debug 版本下跟踪线程被日志串行化。
- 修复方向：改 qCDebug(QLoggingCategory) 并默认关闭；或移植后统一用节流输出。

### T5【P2】computeResponse 每帧做无谓的实数→复数转换
- 位置：objecttracker.cpp:386
- 证据：`elementDivide(num, realToComplex(m_hfDen), m_lambda)` —— m_hfDen 本为实数矩阵，每帧转换一次产生整帧分配。
- 修复方向：elementDivide 增加实数分母重载。

### T6【P1】elementDivide 分母语义不自文档化，误用即发散
- 位置：fftutils.cpp:186
- 证据：`float denom = den[r][c].real() + lambda;`
- 问题：当前调用方传入的 m_hfDen 恰好是 |X|²（实数），结果正确；但接口接受复数却只取实部，一旦有人直接传 FFT 结果，滤波器立即发散且无告警。
- 修复方向：接口拆分为 `elementDivideReal(num, denAbsSq, lambda)`，或加 `Q_ASSERT(std::abs(den[r][c].imag()) < 1e-4)`。

### T7【P2】computeFHOG 三维嵌套 vector，缓存极不友好
- 位置：fftutils.cpp:517-518
- 修复方向：扁平一维数组 `hb*wb*31`。

### T8【P3】TrackResult 缺少红外/可见光模式字段
- 位置：objecttracker.h:12-29
- 问题：reference 跟踪器有 set_infrared_mode（红外用 GST 特征、可见光用灰度+梯度 3 通道），当前结果结构无模式字段，移植后无法区分。
- 修复方向：移植时在 TrackResult/跟踪器参数中增加 mode 字段。

### T9【P2】reDetect 九宫格搜索在 worker 线程内同步执行，遮挡时单帧耗时×9
- 位置：objecttracker.cpp:654-737
- 修复方向：可接受（遮挡帧本来就丢），但需在移植后复核总耗时。

## 三、线程安全与生命周期

### C1【P1】主线程跨线程直接读取 PTZController 成员
- 位置：mainwindow.cpp:662-665
- 证据：
  ```cpp
  if (m_ptzController) {
      panSpeed = m_ptzController->getCurrentPanSpeed();  // 主线程读，对象活在 m_ptzThread
  ```
- 修复方向：把速度并入 angleReceived 信号，在 PTZ 线程内发出。

### C2【P1】日志：全局 mutex + 同步 flush，所有线程日志被串行化
- 位置：logmanager.cpp:114-154
- 修复方向：格式化与写盘分离，写盘线程化（QQueue + 独立写线程）；或 flush 出锁。

### C3【P1】qInstallMessageHandler 非线程安全
- 位置：logmanager.cpp:74、93
- 修复方向：startLogging/stopLogging 内加 `Q_ASSERT(QThread::currentThread() == qApp->thread())`。

### C4【P2】SDK 流回调线程无锁读取 m_isRecording / m_recordThread
- 位置：devicemanager.cpp:512
- 证据：`if (safeInstance->m_isRecording && safeInstance->m_recordThread)` —— 未持 m_mutex。
- 修复方向：`std::atomic<bool> m_isRecording`；m_recordThread 用 mutex 保护或保证创建先于回调注册。

### C5【P1】SDK 异常回调线程直接调用 logout()
- 位置：devicemanager.cpp:385
- 问题：logout() 内部加 m_mutex 并调用 UNIV 网络函数，在 SDK 回调线程里执行有死锁/重入风险。
- 修复方向：`QMetaObject::invokeMethod(safeInstance, "logout", Qt::QueuedConnection)` 切回主线程。

### C6【P2】stopStream 不停解码线程
- 位置：devicemanager.cpp:443-445（start 启动 DecodeThread）vs 460-477（stop 未停）
- 问题：断流后解码线程常驻空转（1s 超时轮询）。
- 修复方向：stopStream() 末尾 `m_decodeThread->stop(); m_decodeThread->wait();`（下次 startStream 会重新 start()）。

### C7【P2】UI 线程直接调用 SDK 网络函数
- 位置：mainwindow.cpp:890-892（onConnectionStatusChanged 里 startStream → UNIV_DEV_RealPlay）
- 修复方向：移入 DeviceManager 内部用 QtConcurrent 执行，完成后再发信号。

### C8【P2】跟踪结果驱动的全量图像重绘
- 位置：mainwindow.cpp:1096-1106（onTrackBoxDraw → displayImage(m_lastFrame)）
- 问题：每帧 fromImage + scaled 执行两次（onFrameReceived 一次、跟踪框更新一次），25fps 下主线程 CPU 占用高。
- 修复方向：缓存 scaledPixmap / 改 QLabel 子类 paintEvent 画框。

### C9【P2】setTarget 在主线程同步执行跟踪器初始化
- 位置：trackingcontroller.cpp:73-94
- 问题：init() 含首次训练（多次 FFT2D + 尺度滤波器训练），实测可达数百 ms，框选确认瞬间 UI 卡顿。
- 修复方向：把 init 也投递到 worker 线程（invokeMethod "initSlot"），完成后发信号再置 Tracking 状态。

### C10【P3】跟踪框选期间 mouseMove 每次事件全量缩放图像
- 位置：mainwindow.cpp:1220-1226
- 修复方向：缓存缩放结果或用 paintEvent 叠加选框。

## 四、FFmpeg 解码/录像管线

### V1【P1】decodeFrame 未规范化 packet 生命周期、EAGAIN 未处理
- 位置：videodecoder.cpp:99-110
- 证据：
  ```cpp
  m_packet->data = const_cast<uint8_t*>(data);
  m_packet->size = size;
  int sendResult = avcodec_send_packet(m_codecContext, m_packet); // 之后无 av_packet_unref
  int receiveResult = avcodec_receive_frame(m_codecContext, m_frame); // 只取一帧
  ```
- 问题：(1) 手工绑定外部缓冲不 unref，FFmpeg 8 下不规范；(2) 解码器有延迟时（B帧缓存）每 send 只 receive 一帧会积压；(3) EAGAIN/EOF 不区分，错误静默。
- 修复方向：send 后循环 `while (avcodec_receive_frame(...) >= 0)` 取完所有帧（当前接口只返回一帧，需要改为回调或返回列表）；packet 用 `av_packet_unref` 规范清理。

### V2【P1】录像 sws 上下文不随输入分辨率变化重建 → 越界崩溃风险
- 位置：RecordThread.cpp:214-226
- 证据：`if (!m_swsCtx) { m_swsCtx = sws_getContext(frame->width, ...) }` —— 只创建一次。
- 问题：首帧后若流分辨率改变（相机切换子码流/变倍缩放），sws_scale 读越界源、写越界 m_yuvFrame，直接崩溃。
- 修复方向：记录 lastW/lastH，变化时 sws_freeContext 后重建，必要时重建 YUV buffer。

### V3【P1】av_interleaved_write_frame 返回值忽略
- 位置：RecordThread.cpp:249
- 问题：磁盘满/IO 错误时静默丢帧，录像文件损坏无提示。
- 修复方向：检查返回值，连续失败 emit errorOccurred 并终止录像。

### V4【P2】录像线程与预览线程各自解码同一路流
- 位置：RecordThread.cpp:269（录像线程内 m_decoder）、DecodeThread（预览解码）
- 问题：双倍解码 CPU 开销。
- 修复方向：可接受（隔离性好），但移植 DSST 后若 CPU 紧张，可改为共享解码帧队列。

### V5【P2】解码器硬编码 H.264
- 位置：DecodeThread.cpp:32、RecordThread.cpp:169
- 问题：相机若配置为 H.265，预览与录像全黑。
- 修复方向：从 UNIV_CFG_VIDEO_ENCODE 的 videoEncType 动态选择 AV_CODEC_ID。

### V6【P2】解码队列满时静默丢最旧帧，无统计
- 位置：ThreadSafeQueue.h:22-24
- 修复方向：加丢帧计数并在 UI 显示，便于评估跟踪输入质量。

### V7【P2】VideoDecoder 分辨率变化时 format 变化不触发重建
- 位置：videodecoder.cpp:112（只比较 width/height）
- 修复方向：比较 `(w,h,format)` 三元组。

## 六、reference 代码自身问题（移植时必须处理）

### R1【P1】roi 边界 clamp 后宽高可能为负 → OpenCV Rect 断言崩溃
- 位置：reference/dsst_tracker.cpp:892-895
- 证据：`roi.width = min(image.cols - roi.x, roi.width);` —— roi.x 被 clamp 为 ≥0 但可接近 image.cols，使 width 为负。
- 修复方向：移植时对 x+w、y+h 与图像边界统一 clamp，负值直接返回失效。

### R2【P1】update() 每帧大量 printf（gst_process 内每帧多行）
- 位置：reference/dsst_tracker.cpp:262、299、354、500-530、628-761
- 问题：实时 25fps 下 stdout 输出严重拖慢帧率（Windows 控制台输出尤其慢）。
- 修复方向：全部改 qCDebug 并默认关闭，仅保留节流的关键状态输出。

### R3【P2】每帧计算量过大：平移采样×2 + 尺度采样×2 + GST×(9+1)尺度
- 位置：reference/dsst_tracker.cpp:569-897（update 流程）
- 问题：红外模式每帧 gst_process 至少跑 9~18 次（每尺度一次 filter2D 组），640×512 下单帧 30~80ms。
- 修复方向：移植时 (1) 尺度估计隔帧执行；(2) GST 参数（filterSize=5）保持不变但把 Mat 通道统一为 CV_32F；(3) 用 cv::setNumThreads 限制防止抢占解码线程。

### R4【P2】get_subwindow 的 x/y 轴命名与 1-based 坐标系混乱
- 位置：reference/dsst_tracker.cpp:183-198
- 证据：`int x1 = floor(pos.y) + 1 - patch_sz.height / 2;` —— x1 实为"行"坐标，且整体 +1/-1 是 MATLAB 1-based 习惯。
- 问题：易在移植时引入 off-by-one；边界 clamp 后提取区域与 model_sz 不一致时直接 resize 拉伸。
- 修复方向：移植时重写为标准 OpenCV 0-based 写法并加注释；行为对齐验证用离线序列回放。

### R5【P3】main_zt.cpp 依赖 gz0084FuncLib 硬件库（不可移植）
- 位置：reference/main_zt.cpp:16
- 说明：仅参考其命令协议语义（0x10 停止 / 0x11-0x13 按目标尺寸启动 / 0x60、0x84 框选启动 / SIFU_CTR 脱靶量反馈），对应我们程序的 TrackingController + MainWindow 链路，不需要移植。

### R6【P3】complex_multiply / complex_conj 逐像素 at<> 访问
- 位置：reference/dsst_tracker.cpp:127-170
- 修复方向：移植时改用 cv::mulSpectrums（一步完成频域乘法+共轭）。

## 附：当前架构数据流（体检结论）

```
[SDK网络回调线程]                [DecodeThread]           [主线程UI]
OnStreamData ──深拷贝QByteArray──> ThreadSafeQueue ──> VideoDecoder::decodeFrame
                                        │                    │ frameDecoded(QImage)
                                        │                    ▼
                                        │            DeviceManager::onFrameDecoded
                                        │                    │ frameReceived(QImage)
                                        │                    ▼
                                        │            MainWindow::onFrameReceived
                                        │              ├─ displayImage()          （主线程绘制）
                                        │              └─ TrackingController::processFrame()
                                        │                       │ invokeMethod(Queued)
                                        │                       ▼
                                        │              [TrackerWorker线程]
                                        │              ObjectTracker::processFrameSlot
                                        │                       │ trackingDone(TrackResult)
                                        │                       ▼
                                        │            TrackingController::computePTZControl
                                        │                       │ ptzControlDelta
                                        │                       ▼
                                        │            MainWindow::onPtzControlDelta
                                        │                       │ ptzMoveDirection(信号)
                                        ▼                       ▼
[RecordThread]                     [PTZ线程]
录像：流数据→解码→编码→mp4          Pelco-D 串口收发
```

体检结论：整体线程模型（回调深拷贝→队列→worker 线程→信号回主线程）是健康的；主要风险集中在 (1) FFT 数学缺陷与跟踪性能（T1/T2/T3），(2) 缺 OpenCV 依赖导致无法移植（B1），(3) PTZ 安全防护缺失（P1/P2），(4) 日志全局锁（C2），(5) 录像分辨率切换崩溃风险（V2）。
